### Design Gaps Identified

1. **72h boundary semantics** (B4): Is `ValidTo == CreatedAt + 72h:00:00` still valid or already expired? Off-by-one risk — the determination sets `ValidTo = CreatedAt + 72h` but the sweep job checks `ValidTo < NOW()`. At exactly 72h, `ValidTo == NOW()` and `< NOW()` is false, so the offer survives one more sweep cycle (up to 15 min). Is this intended?
2. **Discount = 0%** (B2): The invariant only says "≤ 30%". A 0% discount passes validation but produces a useless offer. Is there an implicit minimum? The domain model v2 mentions "≥ 10% (minimum)" but the task invariants only list "≤ 30%". Which is authoritative?
3. **Accept during pending approval** (C3): Can `acceptOffer` be called while `ApprovalStatus = PENDING`? The `validateApprovalStatus on save` checks at save time, but `acceptOffer` is an action — does it go through save validation, or does it have its own guard? Unclear if the action blocks acceptance before approval is granted.
4. **Multi-action in one LUW** (C4): Create → Accept → Create in one transaction. RAP processes determinations on save, but `validateSingleActiveOffer` checks active offers — if the first offer is accepted (status changes) within the same LUW before the second create's validation fires, does the validation see the in-LUW state change? RAP LUW semantics for cross-instance visibility are not guaranteed for validations reading from DB.
5. **Threshold bypass at exactly threshold value** (D3): The rule is "Discount > threshold → approval required". At exactly `Discount == threshold`, approval is NOT required. If threshold is 20% and discount is 20%, no approval — but is `>` or `>=` the correct operator? Business intent unclear.

## Notes for abap-test-generator (Stage 3b)

1. **C1, C2 (concurrency)** require ABAP MUAC or parallel background jobs — these are integration-level tests, not unit tests. Consider generating them as `CL_AUNIT_TEST` with `CL_ABAP_TEST_DOUBLE` for the lock manager, or as manual test procedures documented in the test plan.

2. **B3 (negative discount)** — verify whether `validateDiscountCeiling` checks both bounds. If it only checks `<= 30`, add a lower-bound check. This is likely a real bug.

3. **B4 (exact 72h boundary)** — verify the comparison operator in the expiry sweep job (`<` vs `<=`). Generate a test that creates an offer and waits exactly 72h (or mocks the timestamp) to confirm behavior.

4. **D3 (threshold boundary)** — verify `>` vs `>=` in `determineApprovalRequired`. This is a potential bypass. Generate a test at exactly `threshold` and `threshold + 0.01`.

5. **A3 (direct table bypass)** — verify that a DB CHECK constraint exists on `zret_offer` for `discount_pct <= 30 AND discount_pct >= 0`. If not, this is a **CRITICAL** finding — all application-layer validations are bypassable.

6. **Design gaps (5 total)** should be escalated to the strategic planner / human review before test generation. Cases marked ⚠ may need expected behaviors updated after human resolution.
